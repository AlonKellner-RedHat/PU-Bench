## Bias Analysis: The Auto Prior Distribution Problem

### What is 'auto' actually computing?

When method_prior='auto', the prior is computed as **c × π** (label frequency × true prior).

**Distribution of auto priors in Phase 4:**
- Minimum: 0.0001
- Maximum: 0.9801
- Mean: 0.2500
- Std: 0.3026

### Why this creates bias in fixed prior comparison

The grid has uneven coverage:

| c × π | Auto Prior | Example Configs |
|-------|------------|-----------------|
| 0.01 × 0.01 | 0.0001 | Extremely low |
| 0.01 × 0.5 | 0.005 | Very low |
| 0.5 × 0.5 | 0.25 | Moderate |
| 0.99 × 0.99 | 0.9801 | Extremely high |

**Problem:** A fixed method_prior (e.g., 0.5) is:
- WAY TOO HIGH when true prior is 0.0001 (500× larger!)
- About right when true prior is 0.25
- WAY TOO LOW when true prior is 0.9801 (0.5× smaller)

This asymmetry biases results:
- Low fixed priors (0.01-0.3) fail catastrophically on high c×π configs
- High fixed priors (0.7-0.99) fail catastrophically on low c×π configs
- **Mid-range priors (0.3-0.6) minimize worst-case failure**

### What would an unbiased experiment look like?

**Option 1: Relative error analysis**
- Instead of comparing method_prior to arbitrary fixed values
- Compare method_prior to TRUE prior (c × π) as baseline
- Measure: AUC(method_prior=X) - AUC(method_prior='true')
- Question: Which constant X minimizes loss vs. truth?

**Option 2: Stratified analysis**
- Group configurations by true prior range: [0-0.1], [0.1-0.3], [0.3-0.7], [0.7-1.0]
- Find best method_prior within each stratum
- Check if a single method_prior wins across all strata

**Option 3: Adaptive prior scaling**
- Test priors as MULTIPLES of auto: {0.5×auto, 1×auto, 2×auto, 5×auto}
- Question: Should we scale the computed prior up/down?
- This preserves the relative structure across c×π space
